# 1단계: Big Bang 방식 수작업 배포 설계

## 수작업(Big Bang) 배포 방식의 한계 분석

### 도입 배경
- 초기 인프라는 단일 GCP VM 위에서 모든 구성요소를 수작업으로 배포함
- 프론트엔드(React), 백엔드(Spring Boot), AI 서비스(FastAPI), DB(MySQL)를 하나의 인스턴스에 올리는 방식
- Terraform으로 VM을 프로비저닝한 후, Ansible과 수동 명령어를 통해 애플리케이션을 배포
- CI/CD 환경 없이 직접 쉘 스크립트로 배포를 통제하며, 실제 실습과 실시간 트러블 대응을 우선시한 구조

### 한계점 상세 분석

| 분류 | 사례 | 내용 | 파급 효과 |
|------|------|------|----------|
| **인프라 리스크** | `apt-get` 잠금 충돌 | 백그라운드에서 `apt`가 실행 중이면 `dpkg lock`으로 인해 Ansible 실패 | 반복 배포 실패 및 자동화 차단 |
| **서비스 신뢰성** | FastAPI 서비스 종료 | systemd의 `ExecStart`에 리디렉션(`>>`)이 포함되어 FastAPI 실행 실패 | `/ai/hello` 호출 불가, Spring 통신 오류 발생 |
| **게이트웨이 문제** | 502 Bad Gateway | Spring → FastAPI 통신에서 포트 미열림, 프로세스 죽음 등으로 인해 발생 | React 사용자 단에서 장애로 인식됨 |
| **환경 변수 관리 실패** | Spring 빌드 오류 | `application.properties`에 선언된 `${fastapi.base.url}` 미설정으로 인한 런타임 실패 | `@Value` 주입 오류, 애플리케이션 시작 실패 |
| **버전 불일치** | git 최신 코드 반영 실패 | Ansible이 동일 SHA의 코드만 배포하도록 설정되어 변경 사항 무시됨 | 코드 수정이 반영되지 않아 디버깅 어려움 |
| **로그 관리 부족** | FastAPI 로그 무한 누적 | logrotate 미적용으로 로그 파일이 지속적으로 누적 | 장기 실행 시 디스크 용량 고갈 위험 |
| **보안 경고** | git unsafe repo | Git repo가 안전하지 않다는 이유로 Ansible 내 git 명령어 차단됨 | `safe.directory` 등록 누락으로 자동화 중단 |
| **롤백 부재** | 배포 후 장애 발생 시 수동 복구 | `.bak` 파일이 없거나, `rollback.sh` 미작성 상태 | 장애 시 전체 서비스 장시간 중단 가능성 |
| **프론트엔드 한계** | React 빌드 파일 삭제 시 무반응 | `/var/www/react/assets` 삭제 후에도 헬스체크는 통과함 | 사용자는 브라우저 상에서 빈 페이지 확인 |

### 정리된 주요 리스크 유형
- **자동화 저해**: ansible 실패, git 안전성 경고, 환경변수 미설정
- **가용성 저하**: 프로세스 종료, 포트 충돌, 502 오류
- **디버깅 어려움**: 로그 확인 외에 자동 모니터링 부재
- **운영 복구력 부재**: 장애 발생 시 복원 수단 부족

### 개선 제안
- `.bak` 기반의 자동 롤백 스크립트 작성 및 배포에 통합
- logrotate 설정 및 `.log` 파일 압축 주기 지정
- 모든 서비스에 대해 Ansible 기반 헬스체크 및 조건부 백업 도입
- `/etc/nginx/sites-available/default` 등 주요 설정 자동화 및 TLS 갱신 자동화
- backend/fastapi 모두 `systemd` 서비스 등록 + 상태 기반 재시작 로직 확보

## 서비스별 운영 전략

### Frontend (React)

- **구성 방식**: Vite 기반 정적 웹 애플리케이션. `npm run build` 시 `/dist` 디렉토리에 번들링된 결과물이 생성됨.
- **배포 경로**: `/var/www/react`에 모든 정적 파일을 복사하여 nginx가 서비스 제공
- **롤백 전략**:
  - `/var/www/react.bak` 백업 디렉토리를 유지
  - 롤백 시 기존 `/var/www/react` 삭제 후 `.bak` 디렉토리를 복사
- **장애 사례**:
  - `/var/www/react/assets` 디렉토리 손실 시 헬스체크(`curl`)는 통과하지만 브라우저 렌더링 실패
  - nginx는 정적 파일의 존재 여부를 체크하지 않기 때문에 사용자는 빈 페이지를 보게 됨
- **헬스체크 방식**:
  - `curl -sf https://test.moongsan.com | grep -q '<div id="root">'` 형태로 실제 렌더링 구조 확인

### Backend (Spring Boot)

- **구성 방식**: Spring Boot 애플리케이션을 `./gradlew bootJar`로 빌드하여 `.jar` 파일로 실행
- **배포 경로**: `/home/ubuntu/mock_backend/build/libs/` 내 `.jar` 파일 실행
- **로그 경로**: `/home/ubuntu/backend.log`
- **배포 방식**: Ansible을 통해 Git 레포지토리 클론 → 빌드 → 실행 순으로 배포
- **헬스체크 방식**: 
  - 외부에서 접근 가능한 `/api/hello` 엔드포인트 확인
  - `curl -sf https://test.moongsan.com/api/hello | grep -q 'Hello from Spring Boot'`
- **장애 사례**:
  - application.properties 내 환경변수 누락 시 `@Value` 주입 실패로 애플리케이션 시작 오류
  - 빌드 중 테스트 실패 시 전체 배포 중단 (`./gradlew build` 시 테스트 실패 방지 위해 `-x test` 옵션 사용)
  - `.jar` 실행 시 로그가 파일로 리디렉션되지 않으면 서비스 상태 확인 어려움
- **롤백 전략**:
  - `.bak` 파일을 유지하며 `rollback.sh` 스크립트로 프로세스 중단 후 교체
  - 실행 중 프로세스를 안전하게 종료하고 `.jar.bak` 파일을 원상 복구하여 다시 실행

### FastAPI

- **구성 방식**: `uvicorn` 기반의 Python FastAPI 앱으로 `/home/ubuntu/mock_fastapi/main.py` 위치
- **배포 방식**: systemd 유닛 파일(`/etc/systemd/system/fastapi.service`)을 통해 자동 실행 및 재시작 관리
- **로그 경로**: `/home/ubuntu/fastapi.log`로 stdout 로그 저장
- **장애 사례**:
  - systemd 설정에서 리디렉션 연산자(`>>`) 포함 시 `ExecStart` 오류 발생
  - 포트 점유 중복 시 FastAPI 실행 실패 (8000번 포트 충돌)
  - 파일 손상 혹은 삭제 시 `/ai/hello` API 요청 실패
- **헬스체크 방식**:
  - `curl -sf http://localhost:8000/ai/hello | grep -q 'Hello from FastAPI mock!'`
- **롤백 전략**:
  - `/home/ubuntu/mock_fastapi.bak`를 유지하며, `rollback_ai.sh` 스크립트로 서비스 중지 후 원상복구
  - 포트가 이미 점유된 경우 기존 프로세스 종료 로직 포함
